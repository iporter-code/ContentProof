## 权限与机构协作

organizations.ts 和 Organizations.tsx 增加申请、凭证摘要、审核记录、成员邀请/接受及 owner/admin/editor/viewer。审核人由 OPERATOR_ADDRESSES 配置，不能自审；最后一个有效 owner 不可降级。暂停机构或移除成员会影响后续授权判断。

素材所有者、读者和编辑者分别记录。个人分享默认阅读，可显式编辑；声明详情提供权限选择和分别撤销声明/素材访问。组织编辑授权还需对应成员角色。声明签名权不等于输出素材的再授权权；已下载内容无法撤回。

人工审核工作流已实现，真实机构资质仍需人和外部凭证核对。审核记录在应用数据库，不冒充链上资质证明或第三方认证。

## 持久性与维护

新增 packages/persistence/maintenance.ts 和维护 CLI。备份用 scrypt 派生密钥、逐文件 AES-256-GCM 流式加密，路径/摘要清单也加密认证；全部文件完成后才写完成标记。外置 STORAGE_KEY/STORAGE_KEY_FILE 可封装进加密备份，恢复不依赖原 secret 文件。

恢复只允许不存在的新目录；先认证并校验路径、大小、摘要，再发布暂存目录；拒绝符号链接、路径逃逸和覆盖。文件密钥轮换在暂存副本完成，替换后保留原目录回滚；重加密历史明文素材、私有声明/草稿/导出输入，清除失效导出。外部 secret/provider 自动轮换未实现。

API/链/维护锁用于同机数据目录；跨容器 PID 命名空间及跨主机不在保证范围内，仍须明确停服务。备份含本机链数据库；外部 Besu 状态需另行管理。SQLite v4 补齐关系外键/索引，异常旧关联保存在 migration_rejections，不静默丢弃。升级前应备份，旧程序不能直接打开新版数据库。

## 导出与资源约束

导出由数据库任务推进，加密落盘，ZIP 流带背压；整体含目录开销预算 128 MB、单项 32 MB、最多 3000 项，来源图最多 1000 节点、深度 64；元数据不是无限流式。

网页有进度、取消、相同选择刷新恢复、5 分钟短链接和撤销导出。下载重新检查授权；短链接是持有者凭证，应确认接收人。启动回收严格命名的异常临时文件，过期输出重复尝试清理。

媒体池并发 2、等待 8，sharp 并发 2、缓存 32 MB、超时 15 秒；另有 HTTP 路由及总体准入。验证有 AbortSignal、60 秒预算并周期性让出事件循环，中断标为不完整。这不是任意输入下的硬内存隔离，容器另设资源上限。

## 部署及实际检查

- 编译版 supervisor 部署合约、启动链/API/静态网页，不依赖 tsx/Vite。修复首次容器缺少生产 solc、Linux Ganache 可选 fsevents 元数据、Besu permission 文件不可写等实际错误。
- 非 root 容器、独立卷、secret、健康检查、CPU/内存/PID 限制；不携带运行数据。
- Besu 26.10.0 文件固定 SHA-256，四个验证进程/卷、节点/账户白名单、独立费用账户；生成私钥仅留 data/。
- 实测四节点同区块哈希；停 1 节点仍出块、停 2 节点停止确认、恢复法定人数后恢复。一轮恢复约 41.2 秒，含 JVM 启动及共识轮次退避，不是延迟承诺。
- RPC_URLS 是显式信任的备用源，读写均切换；主 RPC 启动前停机仍完成 8 项业务。不是多数 RPC 证明或恶意 RPC 防护。

四节点全在一台 Windows/WSL 主机，不等于跨机构联盟链。参考 [Besu 共识说明](https://docs.besu-eth.org/private-networks/how-to/configure/consensus/qbft/) 和 [固定发行文件](https://github.com/besu-eth/besu/releases/tag/26.10.0)。

Docker Desktop 4.90 曾通过容器业务及重启检查，随后复发 sailor-ingest.sock 启动错误。scripts/repair-docker-runtime.ps1 仅保留改名两个经过验证的套接字目录，不删除镜像、卷、设置或 WSL 磁盘，是临时恢复。[Docker #460](https://github.com/docker/desktop-feedback/issues/460) 中维护者表示 4.92 起应包含修复；最终升级及重启复测需单独记录，不能用旧成功记录代替当前可用性。

最终处理：两个 Docker WSL 磁盘与设置已冷备份，逐个核对源/备份 SHA-256 一致；官方 4.96.3 安装包的公布摘要和 Docker Inc Authenticode 签名有效，原位升级为 4.96.3.244472，Engine 29.9.2。升级后连续两次完整 stop/start 均成功，没有再改名运行目录；升级前全部容器 ID、镜像 ID/标签、数据卷名保留。原应用容器健康、旧声明仍可读取。数据在本机保留，未上传诊断或删除卷。上述为已观察的复测结果，不保证所有未来 Windows/Docker 情况。

## 最终故障验证及报告

最终容器重建复测发现 PID 复用会把崩溃遗留锁误认为活跃 API。现已将 Linux 锁绑定到内核启动标识、PID 命名空间和进程启动时刻，避免仅凭 PID 判断；旧格式锁仍保守处理。Linux 回归及实际强制终止/重建后恢复健康、读取原声明均通过。该实现依然不是跨主机/跨命名空间的分布式锁，不允许并行部署者共享同一目录。
