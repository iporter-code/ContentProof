## 结论与范围

核心业务已经具备实际实现，现有自动测试、构建、编译版业务和备份恢复检查均通过。但本轮发现了测试没有覆盖的签署语义、交易失败处理、密钥丢失处理、授权撤销、重组恢复和部署运维问题，不能仅凭 170 项测试通过认定生产安全性和稳定性已经完整验收。

覆盖了项目结构与现有台账、前后端身份/签署、素材与机构权限、证据包和协议核验、链访问与任务状态、图片进程隔离、C2PA、存储与备份/轮换、发布与云部署脚本、依赖风险和许可记录。没有连接或修改线上服务器，没有重新执行真实钱包扩展、手机、多机构服务器、Docker/QBFT、真实 Vault 或全部 C2PA 原生向量验收。历史文档的通过记录不等于本轮重新通过。

证据分级：实际复现指隔离本机服务/真实本地 EVM 或直接执行相关模块；模拟复现明确使用受控响应；源码确认指具有明确触发条件的代码路径，本轮未实际部署相应环境。P1 表示应优先处理的主要正确性/信任/可用性问题，P2 表示随后处理的边界与运维问题。

## Bug 与明确缺陷

### A01 · P1 · 客户端未核对待签署字段与用户原始意图

证据：模拟复现。位置：apps/web/src/api.ts:131、apps/web/src/integrity.ts:46。

signAndAnchor 仅接收 draftId，取得服务端 prepare 响应后检查字段格式、操作与数量，再下载服务端指定的文件核对响应中的摘要和大小。它没有带入用户原先提交的字段、父节点顺序、参数和预期素材摘要，也没有用这些本地值重算 claimsRoot/parentsRoot。

本轮在内存中模拟受损业务服务：把 title 换为 server substituted metadata，其余声明格式和文件摘要保持正确。实际执行前端 signAndAnchor 后，它仍生成有效签名。将该签名交给协议验证器，并明确使用模拟的 confirmed/active 链观察，报告为 pass。

这证明了“服务端替换元数据仍会被客户端签署”；没有声称本轮攻击了真实服务器或链。协议签名保护了已签字节，但缺少确认这些字节代表用户原始输入的校验步骤，与项目“不信任业务服务器”的目标存在差距。现有确认框只展示操作、摘要、父数量和签署者，未展示具体字段和有序父信息。

建议：保留本地待签署快照，返回可重算的字段与父承诺材料，在签名前重算并比较；同时核对预期素材、操作/参数、签署主体及可信域。测试应覆盖服务端分别替换字段、父顺序、参数、文件和签名域。

### A02 · P1 · 撤回交易链上失败，接口仍返回成功

证据：真实本地 EVM 复现。位置：apps/api/main.ts:1084；同类未检查回执状态的路径还有 :465、:582、:1098。

撤回接口 await waitForTransactionReceipt 后未检查 receipt.status，直接把任务标为 withdrawn 并返回 txHash。收到回执只代表交易被打包，不保证调用成功。

复现步骤：停止隔离测试链出块，提交当时有效的撤回签名，确认交易进入待处理池，推进链时间使 deadline 过期，再恢复出块。结果：HTTP 200，实际 receipt.status=reverted，链上声明仍 confirmed。此过程使用真实合约与真实签名，没有修改合约或数据库伪造结果。

影响：用户会收到错误的撤回成功反馈；密钥授权等同类路径在回执失败时，也可能推进本地 epoch/审计状态。后者是源码确认，本轮未逐条做失败交易复现。

建议：所有状态改变都以成功回执为前提，失败时返回明确错误；必要时回读链上最终状态，并避免把本地业务状态提前写成成功。

### A03 · P1 · 有历史密文但缺少存储密钥时，自动生成新密钥并继续启动

证据：模块实际复现。位置：apps/api/store.ts:24。

首次生成密钥时没有同时建立 storage-key.id；该标记主要由轮换路径产生。对尚未轮换的数据目录，如果 storage.key 缺失且未配置外置密钥，启动逻辑会直接生成随机新密钥，不先检查目录中是否已有密文。

本轮仅在新建合成目录写入一条加密历史草稿，把该目录的密钥改名保留后重新启动存储模块。结果：startupSucceeded=true、replacementKeyCreated=true、historicalRecordDecrypts=false。未接触实际用户密钥。

密钥原本丢失已经使历史数据不可读取；这里额外的问题是程序继续接受新状态，可能混合两代不可互解的数据，增加故障判断和恢复难度。不能把它描述成“程序自行删除旧密钥”。

建议：非空数据目录缺密钥时明确停止启动；初次建立密钥身份标记，启动时验证密钥与已有数据的一致性。

### A04 · P1 · 核心子进程退出后，启动器不退出也不自动拉起

证据：隔离进程故障复现。位置：scripts/start-app.mjs:54；部署关联 deploy/compose.yml:23、deploy/Dockerfile:12。

start() 对子进程的 error/exit 只记录日志，没有让父启动器失败退出，也没有恢复子服务。

本轮通过父 PID 精确定位本次隔离测试启动的 API 子进程并终止它。1.5 秒后 API 已不可访问，父启动器 exitCode 仍为 null。测试结束后正常关闭了本次启动器及其余服务。

对默认 Docker Compose，restart: unless-stopped 不能仅凭健康检查变成 unhealthy 就重启容器，因而可能留下存活但不可服务的容器。云端另有每分钟健康检查 timer，可缓解这种情况，不能把云端描述为完全没有恢复机制。

建议：定义核心子进程异常退出的统一策略：终止受管服务并让父进程非零退出，或有界地重启子进程；覆盖 API、链、启动失败和退出码 0 的非预期退出。

### A05 · P2 · 授权撤销没有约束已存在草稿的后续签署

证据：真实 API/EVM 复现。位置：apps/api/main.ts:736、:787、:863。

导入草稿时检查 assetEdit；之后 prepare 直接读取素材元信息，signatures 主要检查签名密钥、nonce 和 deadline，没有重新验证该素材当前的读取/编辑授权。

复现：A 给 B 编辑授权，B 创建导入草稿，A 撤销素材授权。B 再读取素材返回 403，但通过 API 仍能 prepare、提交自己的签名并登记成功，任务为 confirmed。

这不表示撤销能够追回已下载文件，也不是对链上自由签署的限制；缺陷是平台已经拒绝素材访问，却仍接受基于旧草稿的新业务操作。浏览器正常签署会先下载文件，因而可能被 403 阻止；本轮复现通过直接 API 调用完成。

建议：明确撤销对存量草稿的语义，并在 prepare、签名提交和排队执行等边界重新检查所需授权。若刻意允许存量草稿继续，应在产品和权限规则中明确表达。

### A06 · P2 · 链记录恢复后，任务仍保持 orphaned

证据：真实回滚/重新登记复现。位置：apps/api/main.ts:1052。

GET jobs 会在链记录消失时把 confirmed 改成 orphaned，但在重新观察到 confirmed 时没有把 orphaned 恢复为 confirmed。

复现：登记前创建 EVM 快照，登记后任务 confirmed，回滚使任务变为 orphaned，再直接向真实链重新提交同一声明。之后查询得到 state=orphaned、registrationStatus=confirmed。

影响：前端 waitForJob 将 orphaned 当作失败；用户看到的任务状态与链状态不一致。已有 anchor 重试入口可以重新排队，这能缓解问题，但不是查询状态自动恢复。

建议：区分历史交易结果与当前登记状态，给观察状态建立完整转移规则，至少覆盖 absent→confirmed 和 withdrawn 分支回滚后的恢复。

### A07 · P2 · 反向代理后不同用户共用 180 次/分钟限额

证据：注入请求复现及部署配置确认。位置：apps/api/main.ts:101、:124；deploy/cloud/enable-https.sh:35。

云端 Nginx 设置 X-Forwarded-For，但 Fastify 没有设置可信代理，默认限流按实际 socket IP 分组，代理后的来源通常都变成 127.0.0.1。

本轮向实际应用实例依次注入不同 X-Forwarded-For、相同代理 socket 来源的请求，第 181 次返回 429。它验证应用配置行为，本轮没有对线上代理施加流量。

影响：用户轮询和一个活跃用户的请求可能耗尽所有用户的限额；健康接口也共享限流。

建议：只信任实际受控的代理来源，再按可信客户端地址/登录身份设计限流键；单独规划健康探针预算，避免直接信任任意客户端伪造的转发头。

### A08 · P2 · 再次部署会整体覆盖运维配置

证据：源码确认，未执行服务器部署。位置：deploy/cloud/provision.sh:38。

每次执行 provision.sh 都以固定模板重写 /etc/contentproof/app.env。原先人工配置的 OPERATOR_ADDRESSES、关闭注册策略、外部 RPC、Vault 配置及其他定制参数不会被保留；模板还固定写入 REGISTRATION_MODE=open。

影响：后续升级可能清空机构审核人配置、重新开放本来关闭的注册，或改变原先确定的运行策略。模板未配置审核人，也意味着首次部署后还需要独立完成机构审批人的设置。

建议：把首次初始化与后续升级分开，保留持久配置并验证必要字段；对配置变更给出可审查的差异。

## 依赖与供应链风险

本轮 npm audit --omit=dev 返回 37 个受影响依赖条目：5 critical、24 high、6 moderate、2 low。原始 JSON：data/audit-2026-10-24/npm-audit-production.json。

5 个 critical 条目均位于 Ganache 的嵌套依赖：cipher-base、elliptic、pbkdf2、sha.js、webpack。默认持久化参考链确实运行 Ganache 7.9.2，因此这些依赖会随默认部署一起分发；其中有些属于内部工具链，是否能被当前服务调用路径触发，需要单独分析，不能按扫描等级宣称本项目已存在远程严重漏洞。

当前 sharp 0.34.5/libvips 8.17.3 也处于扫描告警范围。[维护者公告](https://github.com/lovell/sharp/security/advisories/GHSA-f88m-g3jw-g9cj)说明部分问题与 GIF/TIFF/VIPS 解码有关；本项目 PNG/JPEG 白名单和子进程隔离能缩小攻击面，但不代表依赖风险已经全部消除。本轮没有执行恶意原生媒体漏洞利用，也没有直接升级 sharp；升级会改变 engineDigest 和图片编码，需连同既有声明复算策略一起评估。

OpenZeppelin 5.2.0 的扫描项涉及 Bytes.lastIndexOf；当前合约没有调用该函数，不能据此直接认定部署合约有可利用漏洞。详见[原始公告](https://github.com/OpenZeppelin/openzeppelin-contracts/security/advisories/GHSA-9rcw-c2f9-2j55)。Ganache 内 ws 的已知风险也需结合只监听本机的部署边界判断，见[维护者公告](https://github.com/websockets/ws/security/advisories/GHSA-96hv-2xvq-fx4p)。

处理重点应为依赖调用可达性和默认分发范围，不能盲目执行 audit fix --force；扫描给出的 Ganache 修复建议包含降级主版本，不能当作正确迁移方案。

## 尚不足或未完成的内容

1. **24 小时验收未完成。** 本轮只读查询已有长测：最近记录 elapsedSeconds=34205.785（约 9.50 小时）、completedWorkflows=2281、reauthentications=18，passed=false、complete=false；正常权限复核 processAlive=false。当前状态为 interrupted-or-not-started，没有最终通过报告。进度中的 errors=[] 不代表已通过；本轮没有查明停止原因，没有重启或归档该历史任务。
2. **生产拓扑仍有边界。** 默认单机参考链不能提供独立机构间的共识信任；现有 RPC fallback 是可用性切换，不是多个 RPC 的一致性交叉验证。多机构独立主机、外部 QBFT 灾备及恶意节点/非对称网络仍需分别验收。
3. **浏览器与真实钱包覆盖不足。** 现有 CUA 脚本是浏览器操作辅助，不在 npm test 中自动执行。机构审批/权限全流程、真实钱包扩展、移动端和完整云端浏览器流程仍不能由单元测试代替。
4. **故障测试缺少本轮发现的窗口。** 建议补充失败回执、授权撤销后的旧草稿、链状态重新出现、代理多用户限流、密钥缺失和核心子进程退出。已有正常业务与密钥轮换测试通过，不覆盖这些情形。
5. **备份仍是单机恢复辅助。** 云端每日停机备份的保留期、自动清理、磁盘空间告警和独立灾备职责尚待落实；持续增长的备份可能占满系统盘。此项为部署策略不足，本轮未做磁盘耗尽试验。
6. **工程可维护性与版本管理不足。** API 主文件约 1297 行，网页主文件约 1817 行；权限、链交易、任务与界面职责集中，增加遗漏状态分支的概率。本轮未发现 CI 工作流；Git 当前没有任何提交，源码全部未跟踪，缺少可核对的版本基线与回滚点。
7. **性能结论仍有限。** 既有 1000 节点协议测试对链观察和媒体复算使用替身，不能推导真实链/图片吞吐；突发上传限流通过也不等于持续全业务容量。前端主包存在 500 kB 警告，建议在功能正确性后再处理按页面拆分。
8. **许可缺口仍在。** 缺完整原文的 4 项是 abstract-logging@2.0.1、acorn-import-assertions@1.8.0、async-eventemitter@0.2.4、mcl-wasm@0.9.0。已有摘要/引用核验通过不能替代这些原文和分发义务的补齐。
9. **研究与协议扩展未完成。** 当前 C2PA 为原生内嵌离线核验入口，不是完整 C2PA 签署、在线吊销、远程清单或 CAWG 身份认证；音视频受控编辑、可信时间戳、ZK、水印及模型方认证仍需独立实现。原计划中的批量合约登记、多个业务实例协作和增量图加载也未见完整落地。
10. **文档存在陈旧描述。** docs/LIMITATIONS.md 仍写容器和规模压测未实测；docs/THREAT_MODEL.md 仍把已实现的备份/轮换等列为生产缺口；IMPLEMENTATION_STATUS.md 仍写长测运行中。需要区分历史快照与当前状态，避免给验收者互相冲突的结论。

## 建议处理次序

先处理签署意图核对、链上失败回执、密钥缺失时拒绝启动和核心服务退出处理；再统一授权/任务状态机和代理限流，保护升级时的持久配置。随后针对这些边界补回归，重新执行真实业务和灾备验收，并完成连续 24 小时记录。依赖风险需同步做调用可达性评估，维护版本基线与许可台账。
